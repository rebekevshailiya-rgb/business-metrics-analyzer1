# Архитектура Business Metrics Analyzer

Практическое занятие № 4. Команда: Михаил, Саша, Илья.

## 1. Обзор системы

Система проектируется для ООО «Ритейл-Аналитика»: импорт продаж, расчёт четырёх KPI, дашборд, формирование и экспорт отчётов. Эта документация описывает **целевую архитектуру**, а не реализованный веб-сервис. Существующий `main.py` остаётся консольным прототипом; Docker, БД и API в этой работе не развёрнуты.

Основание: [требования](../business_requirements.md), [User Stories](../user_stories.md), [Use Cases](../use_cases.md), [backlog](../product_backlog.md). По ПЗ № 4 объём увеличивается с тестовых 10 000 до 1 000 000 записей, добавляются JWT, облачное Docker-развёртывание, интеграция с источником через API и PDF-экспорт. Это расширение учебной модели ПЗ № 2; оценки прежнего backlog не считаются автоматически достаточными для нового объёма.

## 3. Архитектурный стиль

Выбран слоистый модульный монолит с инверсией зависимостей. Presentation вызывает Application; Application использует Domain и собственные порты; Infrastructure реализует порты. Domain не импортирует FastAPI, SQLAlchemy или Redis. Сборка зависимостей выполняется в composition root, а не в моделях.

API и worker запускают **одно приложение из одного образа** разными командами. Worker изолирует длительные задания от HTTP-процесса; это не независимые бизнес-микросервисы. AuthService, KpiService, SalesImportService и ReportService являются модулями, а не отдельными C4-контейнерами. C4-контейнер не равен Docker-контейнеру.

Микросервисы отклонены: отдельные релизы, сетевые контракты, распределённые транзакции и эксплуатация не оправданы небольшой командой. Горизонтальное масштабирование API возможно; ограничение монолита — совместный выпуск и грубая гранулярность масштабирования, а не полный запрет нескольких реплик.

### Импорт и целостность

POST `/imports` проверяет права и ограничения файла, сохраняет оригинал в закрытое хранилище и создаёт запись задания/событие outbox в PostgreSQL. Возвращается 202 с `job_id`, не обещание готового отчёта. Dispatcher надёжно передаёт событие в очередь; worker обрабатывает задания с повторными попытками.

Worker читает файл порциями и записывает staging-строки с `import_id`. Ошибки строк, отсутствующие колонки и дубли внутри файла фиксируются отдельно. При любой ошибке импорт получает `failed`; staging не участвует в запросах KPI. Повтор неизменного набора определяется по checksum + области доступа, а продажи защищены уникальным `(source, external_sale_id)`.

После полной проверки одна транзакция публикует весь набор, обновляет дневные агрегаты, увеличивает `dataset_version`, пишет аудит и отмечает задание успешным. Частичные staging-пакеты не видны пользователям. Сбой до commit сохраняет прежнее опубликованное состояние. Для существующего ID с изменёнными значениями по умолчанию отклонение до согласования правил обновления. Тяжёлые XLSX-файлы ограничены по размеру и строкам; расширение листов не загружается без ограничений в память.

### KPI и кэш

Выручка = сумма выручки завершённых продаж; средний чек = выручка / число завершённых продаж; конверсия = успешные / все закрытые сделки × 100%; рентабельность = (выручка − затраты) / выручка × 100%. Денежные величины — Decimal/Numeric. При нулевом знаменателе результат `null` и подпись «Не определён»; старое условие `0.0` в консольном прототипе не переносится в веб-контракт.

Ключ кэша содержит область доступа, период, фильтры, версию правил и `dataset_version`. Смена версии исключает выдачу старого набора после commit. Авторизация выполняется **до** обращения к кэшу. Агрегаты хранят суммы и счётчики; проценты между отделами не усредняются без весов. При отказе Redis система обращается к PostgreSQL; восстановление корректности важнее скорости, SLA может ухудшиться.

### Роли и безопасность

Директор и аналитик имеют доступ ко всем отделам; руководитель — к своему; менеджер — к своим сделкам; администратор управляет доступом, но не получает финансовые данные автоматически. Все запросы и фоновые задания проверяют права; область из тела запроса не считается доверенной. Блокировка проверяется по актуальному статусу пользователя, а не только подписи JWT.

JWT проверяется по разрешённому алгоритму, подписи, сроку, issuer/audience; короткоживущий access-токен (проектное значение 15 минут), refresh с ротацией и хранением хеша. Пароли — стойкий хеш; секреты вне Git. HTTPS, закрытые БД/Redis/S3, выдача отчёта после проверки владельца; ограниченный срок ссылки скачивания. Аудит пишет субъект, действие, объект, результат, время и correlation_id, но не пароль/токен. Эти меры — проектные решения, не результат проведённого аудита безопасности.

## 6. Паттерны

Выбраны семь паттернов: Repository, Unit of Work, Service Layer, DTO, Strategy, Factory, Adapter. Таблица по функциональным областям и исполняемые примеры: [patterns.md](patterns.md). Не требуется применять все паттерны в каждом модуле: это создало бы искусственные абстракции.

## 7. Технологический стек

Целевой стек: Python 3.12+, FastAPI/Uvicorn, SQLAlchemy, PostgreSQL, Redis для очереди и кэша, Celery worker, Nginx, Docker, S3-совместимое хранилище. Web UI — HTML/JavaScript с графиками. Импорт/экспорт Excel — openpyxl; PDF — ReportLab. Точные совместимые версии и digest образов фиксируются перед реализацией в lock-файлах; `latest` не используется как воспроизводимая спецификация. Текущий `requirements.txt` консольного прототипа не выдаётся за зависимости целевой системы.

## 8. Ограничения и компромиссы

SLA ≤ 3 с — требование, пока не измеренное достижение. Предлагаемый профиль проверки: 1 млн записей, 10 одновременных пользователей, типовые фильтры; измерить p95 и максимум отдельно для холодного/горячего кэша, а также границ отделов. Точный SLA согласуется с заказчиком. План тестов: дубли/ошибки импорта, остановка worker, rollback, повтор задания, недоступность Redis, блокировка пользователя, изоляция отделов и скачивания отчётов.

Один облачный узел — точка отказа; схема не обеспечивает высокой доступности. Очередь и кэш используют разные экземпляры Redis, чтобы вытеснение кэша не удаляло задания. Доставка заданий допускает повторы, поэтому операции идемпотентны; outbox закрывает разрыв между commit БД и отправкой сообщения. Ограничения файла, лимиты ресурсов, резервное копирование и мониторинг требуют проверки до промышленного запуска.

## 9. План развития

Сначала контракты и модульные тесты Domain, затем API/права, импорт и хранилища, агрегаты/отчёты, нагрузочная проверка. US-06/US-07 остаются этапами развития; SMTP-адаптер и API-источник — предусмотренные точки расширения, интеграция с реальной 1С не заявляется выполненной. Микросервисы рассматриваются только при измеренной необходимости независимых релизов/масштабирования.
